## 2 产品主线（澄清：主线从来没变）

用户问「产品主线变了？我都不知道」——**是我的表述错误**。

原始需求文档 `requirements-v1/personal-knowledge-base-requirements-v1.0.md` 第 10 行原文：

> 「第一版只供产品所有者本人使用，**核心流程为内容收集、可靠存档、AI辅助理解、稍后阅读和长期整理**」

**用户的真实工作流（第一性需求）**：

```
公众号看到推文 → 微信转发 → 自动剪藏入库（成一篇排好版的文章）
                → 小幅度编辑 + 加自己的想法
                → AI 总结 / 改写
```

用户原话：「**AI 是非常重要的，我不是要做一个传统的笔记软件！**」

**变的是执行顺序，不是主线。** 看门狗按任务表编号做成了"外壳 + 编辑器外观"，
而用户要的是这条流水线能真正跑通。

## 3 关键路径重排

```
M4 表格可用  →  M3 剪藏入库  →  编辑器可用  →  AI
```

**为什么 M4 变成第一环**：用户选定剪藏内容以**表格**形态呈现（见 §4），
所以多维表不再是"第 5 模块"，而是剪藏的前置依赖。

| 原任务表顺序 | 现在 | 原因 |
| --- | --- | --- |
| M1 外壳 → M2 编辑器 → M3 剪藏 → M4 多维表 → M9 AI | **M4 → M3 → 编辑器 → AI** | 剪藏要落进表格 |

## 4 剪藏内容的形态（用户明选形态二）

用户在我给的三个选项中选**形态二**，理由：

> 「**形态二才是我需要的，因为我更加喜欢有条理的表格**」

| 形态 | 内容 | 取舍 |
| --- | --- | --- |
| 一 | 剪藏直接变成可编辑文档 | 最省工，但文章多了会乱 |
| **二 ✅** | 剪藏落进表格的一行 → 点行右侧展开记录页 | **用户选定** |
| 三 | 收件箱 + 归档成文档 | 最贴整理习惯，但要两套东西 |

**为什么不是"按来源分表"**：组合筛选（未读 + 某公众号 + 本周）只有在**一张表 + 字段筛选**下才自然；
按来源分表会让筛选器失去意义。「剪藏库总表 + 来源类型字段」也与需求文档一致（「来源类型」是字段不是表）。

### 4.1 侧栏结构（选项 C）

```
侧栏
├─ 📊 剪藏库          ← 全部剪藏内容，统一入口（靠筛选器分流）
├─ 📁 磷化工           ← 你自己建的分类
├─ 📁 锂电
└─ 📄 随手记
```

### 4.2 正文存哪：路线乙（记录页承载正文）

**表格只管元信息，正文存在独立的「记录页」里。**

- 与真 FlowUs 一致（**记录 = 页面块 type0**），需求文档 M4-T07「记录页」也是这个
- **不用长文本单元格装 2000 字正文**：表格会被撑高、给不了富文本渲染、AI 也难处理
- 代价：多一层记录页数据结构（M4-T07 未做）

### 4.3 记录页结构（用户逐项确认）

```
┌────────────────────────────────────────────────┐
│  磷酸铁锂成本分析                    ← 标题（可改）│
│  公众号 │ XX科技                              │
│  作者   │ 张三      ← 属性区 = 表格里的列，同一份数据
│  原文链接│ https://mp.weixin.qq.com…            │
│  收藏时间│ 2026-11-08 14:22                     │
│  标签   │ 锂电 · 正极                          │
│  AI状态 │ ✓ 已生成    [✦ 总结] [✦ 提炼要点]    │
│  ─────────────────────────────────────────────  │
│  【作者原文】  ← 剪藏的正文，**只读**            │
│  碳酸锂价格...（图片）                          │
│  ─────────────────────────────────────────────  │
│  【我的想法】  ← 你写的，可编辑                  │
│  （选中一段 → 浮出 [改写][续写][翻译]）           │
└────────────────────────────────────────────────┘
```

1. **「作者原文」与「我的想法」物理分开**，原文**只读**（需求文档 NOTE-03 同款）
2. **属性区与表格列共用同一份数据**，不另设一套
3. **详情页形态 = 右侧展开，长文可展开成整页**（平时用右侧，长文按一下变整页）
4. **AI 简介 = "生成一份旁边的摘要让你采纳"** → AI 结果单独存，点「插入到正文」才合并

## 5 AI 路线图（B → B+ → C，C 必须保留）

用户原话：

> 「**最终的目标是 C. 全局对话式**……所以我可以接受**第一版 AI 功能就做到 B 就结束**，
> 但是你**一定要把完整要做成什么样的 AI 记录下来**，哪怕记到最后面后续版本中」

| 阶段 | 能力 | 前置 |
| --- | --- | --- |
| **B（第一版）** | 选区改写 / 续写 / 翻译 + 整篇摘要 / 提炼要点 / 生成标签 | 编辑器能选中、剪藏能入库 |
| **B+** | AI 简介写进剪藏页元信息（需求文档的公众号资料库有「AI简介」「AI状态」两列） | 同上 |
| **C（终版）** | 全局对话式：问「我之前剪藏的磷化工文章里怎么说 XX」→ 跨库检索 + 引用 | 搜索（M5）/ 多维表（M4）/ 向量索引 |

→ **C 需要的检索能力要同步记进 M5（搜索）任务**，别让它掉队。

### 5.1 AI 入口（两个都要）

1. **选区级**：正文里选中一段 → 浮出小工具条（改写 / 续写 / 翻译…）
2. **整篇级**：详情顶部工具条（总结 / 提炼要点 / 生成标签…）

### 5.2 AI 结果的存储原则

**单独存，不直接覆盖正文**。用户点「插入到正文」才合并 —— AI 写错了能直接丢掉。
（需求文档：AI结果"不是作者原文，不覆盖快照"）

## 6 模型接入：通用"添加供应商"入口

我第一版理解成"抄 workbuddy 的 41 个模型清单"，用户纠正：

> 「不是让你去把全部模型抄下来……而是**标准 agent 软件中成熟的添加自定义 API 的样子**，
> 是一个**通用的添加入口**，你可以**内置几个国内大厂的链接**，比如 DeepSeek、minimax、Qwen、GLM 等等，
> 然后**给一个自定义接口**」

**正确形态**（照用户提供的两张截图）：

```
模型设置
├─ 左侧：供应商列表          右侧：选中供应商的配置
│   ● BigModel (智谱)         Base URL    [https://open.bigmodel.cn/api/paas/v4/]
│   ● DeepSeek                API 格式    [OpenAI 兼容 ▾]
│   ● MiniMax                 API Key     [•••••••• 👁]
│   ● 通义千问                模型列表    [● deepseek-chat  ＋添加模型]
│   ● 自定义供应商              ...
```

「添加模型」弹窗：供应商下拉 / 接口地址 / API Key（带**测试连接**）/ 模型名称 / 高级配置（工具调用、图片输入、思维模式）。

**内置几个国内大厂 base_url 预设 + 一个自定义入口**；不预置模型清单、不绑定单一厂商。

技术参考：workbuddy 的 `~/.workbuddy/models.json`（41 个模型全部走 OpenAI 兼容 `/chat/completions`，
也有直连 openrouter / 讯飞 / 火山）——**只借字段结构与协议兼容，不抄清单**。
⚠️ 该文件含 apiKey，**只读结构、绝不写入本项目任何文件**。

## 7 表格：通用骨架，不写死字段

用户原话：

> 「**要**，你可以理解为你就做一个**骨架**，具体公众号剪藏这个表格要哪些字段我到时候自己来，
> **你把骨架和基础功能做好**」

→ **M4 必须是通用多维表引擎**，需求文档里那 10 列只是"他将来会建的示例"，不是我们的实现清单。

### 7.1 第一版必须提供

- **列管理**：加列 / 改列名 / 选字段类型 / 改字段类型 / 删列 / 拖列序
- **字段类型集**：文本 · 长文本 · 单选 · 多选 · 数字 · 日期 · 复选框 · 链接 · 人员
  （公式 / 关联 / 汇总属 M4-T04「第二批」，也要做，不能推后）
- **单元格**：编辑 + 保存
- **视图**：表格视图至少一个真能用
- **筛选**：**多条件组合**（用户明选：「日常就要『未读 + 某个公众号 + 本周』这种组合筛选」）
- **排序**：单列升 / 降
- **行操作**：增行 / 删行

### 7.2 改字段类型的安全边界

需求文档 M0-T26 明确警告过：「**绝不在用户现有表上改类型——单选改数字会丢选项值且不可逆**」

→ 改类型时，若原数据不能无损转换，**提示一次并确认**，不默默丢数据。

### 7.3 「存档状态」「AI 状态」必须是可筛选字段

用户要「只看 AI 还没生成的，批量去生成」→ 这两列**要能筛**，不能只做文字标签。

### 8.1 多人协作（将来可能）

调研结论（workbuddy 本机数据 + 程序包）：

- workbuddy 的项目 = **云端协作的 AI 工作上下文容器**，层级是「项目 → 会话/任务 → 文件树」，
  文件树属会话级（按 cwd 展开），**没有**「页面 → 子页」文档树
- FlowUs 的空间 = **共编文档容器**，主实体是「页面」

→ 若要做"多人共编同一篇文档"，**FlowUs 的模型更贴**；workbuddy 项目形态适合"共享 AI 上下文"。

**当前自用，按项目/主题分类。** 多人协作的底层（账号/权限/服务端）暂不做，但数据模型别堵死。

## 9 字体与图标（都要换，方案另议）

- **字体**：当前栈 `my-quote → PingFang SC → Microsoft YaHei → …`，但 **my-quote 没打包**
  （`client/assets/fonts/` 空、pubspec fonts 段是注释）→ 实际落到微软雅黑。
  `my-quote` 是 FlowUs 私有字体，不能搬。
  - 已测事实：真 FlowUs 在 Windows 上**同样**落到微软雅黑、字宽一致（83/97/96 vs 83/98/96）
    → **像素级对齐不需要打包 my-quote，可以自由换字体**
  - 候选：LXGW 霞鹜文楷（OFL）/ 思源系 / Inter 等
- **图标**：105 个 SVG = **96 个 FlowUs 自研 `Ic*`**（填充式 20 网格）+ **9 个 Lucide**（ISC，可自由用）。
  自研那批照抄有侵权风险。
  - **"用开源图标库"与"看起来跟 FlowUs 一模一样"无法同时满足** → 需单独决策

## 10 施工顺序与交付节奏

### 10.1 剪藏先做哪个（用户选选项 1）

**选项 1 = 先做"能用的剪藏"，不等微信。**

1. 服务端从 CLI 变成**常驻 HTTP 端点**（现在只有 CLI）
2. 客户端设置页（服务端地址 / 目标表 / 自动拉取开关）+ 手动「拉取」
3. 表格引擎（加列/填值/组合筛选/排序/行操作）
4. 详情页 + 编辑器真能用（点行 → 读 → 改 → 存 → 可选中）
5. AI（模型设置 + 选区改写 + 整篇总结）
6. **微信入口最后单独验**

**理由**：剪藏价值 90% 在"文章进来之后能读能改能被 AI 处理"，与微信入口无关；
服务端已有 22 条真实剪藏数据可当样本；微信那条是**前置未知项**，
卡住它会挡住所有其它工作。

### 10.2 交付节奏（用户选 B）

> 「**一次性把表格做完整**，或者说，我不着急那么早用，
> 但是我希望你告诉我能用的时候是**真的能用**而不是一个壳子」

→ **不要为了"早点给用户看"而交半成品**。可以长时间没有新东西，但交出来的必须真能用。

### 10.3 真实数据接入（用户选"接"）

- 用户那 8 篇笔记 = 测试数据，不重要；FlowUs 导出的 131 篇在 FlowUs 侧，安全
- **风险控制**：演示库与真实库分离（已修，`ce7112c`）、写操作先在演示库验证、备份机制保留

### 10.4 服务端现状（不是从零开始）

| 环节 | 状态 |
| --- | --- |
| 微信接入 | ✅ `server/src/sources/wecomClient.ts`（**企业微信** qyapi + 分页游标） |
| 抓正文图片 | ✅ `server/src/fetch/`（article / sanitize / images / snapshot） |
| 对象存储 | ✅ `server/src/store/r2ClipStore.ts` |
| 剪藏流水线 | ✅ `server/src/pipeline.ts` |
| **服务端 HTTP 端点** | ❌ 只有 CLI |
| **客户端拉取** | ✅ 250 行真实代码 `client/lib/clip/clip_pull.dart`（读清单 → 逐条取 → 自动建列 → 写入多维表 → 下载图片） |
| **客户端 UI** | ❌ 设置页没有服务端地址 / 目标表 / 自动拉取 |

**⚠️ 微信那条链路的风险**：服务端接入的是**企业微信**（`qyapi.weixin.qq.com`），
不是个人微信的"转发给朋友"。需求文档 CLIP-01 要求"在微信文章中转发给剪藏入口"，
**能否真的从个人微信转发进系统必须真机验证，不能靠推断**（需求文档原话）。

真实剪藏样本：`server/data/clips.db` 22 条（公众号 13 / B站 2 / 小红书 3 / 抖音 1；
状态 complete 15 / partial 5 / failed 2）。
