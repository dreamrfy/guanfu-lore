## 1 底层事实：FlowUs 是 Tiptap/ProseMirror 血统 + Notion 式存储

两点已由实测确认：

1. **块类型是数字**（不是字符串）——Notion 那一套。实测出现的 `type` 值全部是 `number`。
2. **块表是以 UUID 为键的对象**，不是数组；父子关系靠 `parentId` / `subNodes` 两条字段。

## 2 接口面（实测可用的端点）

| 端点 | 返回 | 用途 |
| --- | --- | --- |
| **`GET /api/docs/{docId}`** | `{code, data:{blocks, collectionViews, discussions, comments, roles}}` | **文档全文（核心）** |
| `GET /api/spaces/{spaceId}/root` | 页面树（43KB 量级） | 侧栏页面树 |
| `GET /api/spaces/{spaceId}/visitsHistory` | 访问历史 | — |
| `GET /api/users/{userId}/root` | 用户根 | — |
| `GET /api/activity/list` | 动态 | 页面「动态」 |
| `GET /api/ai/config` | AI 配置 | M9 参考 |
| `GET /api/rag/capabilities` | AI/RAG 能力 | M9 参考 |
| `GET /api/spaces/plans` | 套餐 | 容量提示 |

> **对 M6（导入）的价值**：搬历史数据时，`/api/docs/{id}` 就是**权威数据源**，比解析导出的 Markdown/HTML 更完整（含 icon/cover/属性）。已记入 M6-T05 的可选路径。

## 3 块（block）通用结构

每个块都有这些字段（实测键名与类型）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `uuid` | string | 块 id，也是 `blocks` 对象的键 |
| **`type`** | **number** | **块类型（数字）** |
| `parentId` | string | 父块 id |
| **`subNodes`** | array | 子块 id 列表（**块树**） |
| `title` | string | 块标题（页面块用） |
| **`data`** | object | **块的实际内容**（含行内文本，见第 4 节） |
| `views` | object | 该页挂着的多维表视图 |
| `status` | number | 状态 |
| `permissions` | object | 权限 |
| `spaceId` | string | 所属空间 |

| `backgroundColor` / `textColor` | string | 块级着色（对应块菜单的「颜色」） |

## 4 行内文本：`data.segments`

**正文不是纯字符串**，而是分段数组。段的结构实测为：

```
{ text: string, type: number, enhancer: object }
```

- `text` —— 文字
- `type` —— 段类型（数字）
- **`enhancer`** —— 行内样式（加粗/斜体/下划线/删除线/代码/链接等）

> 这正是**行内样式**（M2-T05）的存储位置。具体 `enhancer` 里有哪些键、`type` 各值代表什么，需要下一步对照采集才能定名。

## 5 实测到的块类型（数字 → 已知线索）

跨 12 篇文档统计，共出现 **7 种**数字类型：

| type | 块数 | `data` 里的键 | 判定 |
| --- | --- | --- | --- |
| **0** | **157** | format, segments, pageFixedWidth, **collectionProperties**, **icon**, **cover**, coverPos, **description**, **directoryMenu**, **collectionCardColor**, copied_from | ✅ **页面块**（含页面图标/封面/描述/集合属性→"页面即数据库页面版"） |
| **1** | **136** | format, segments, pageFixedWidth, **level** | ⏳ 有 `level`（层级）→ 标题类或列表类，**待确认** |
| 7 | 20 | level, format, segments, pageFixedWidth | ⏳ 同样带 `level`，**待确认** |
| 4 | 18 | format, segments, pageFixedWidth | ⏳ **待确认**（最简结构，疑为段落） |
| **18** | 4 | **schema**, format, segments, description, pageFixedWidth, **collectionPageProperties**, icon, cover, coverPos | ✅ **多维表块**（带 `schema` 字段定义） |
| 19 | 2 | **schema**, cover, coverPos, segments, **collectionPageProperties** | ✅ 多维表相关（疑为视图/记录页） |

> ⚠️ **必须说清楚**：`0`（页面）与 `18/19`（多维表）判定是高置信的（字段特征明显）。**其余 4 个数字我无法仅凭字段名断定中文名**——硬猜就是编。已拆为 **M0-T17**：手动建一篇"每样块类型一个"的文档，逐个对照，把数字映射成名字。

## 6 多维表模型（顺带采到，M0-T09 可直接用）

**块上的**：
- `data.schema` —— 字段（列）定义
- `data.collectionPageProperties` —— 集合页面属性
- `data.collectionProperties` —— 集合属性
- `block.views` —— 该页挂载的视图

**`data.collectionViews`（按 view uuid 为键）字段实测**：
`uuid, type, title, format, collectionId, shareId, pageSort, status, spaceId, parentId, version, createdAt, createdBy, updatedAt, updatedBy, deletedBy`

**视图类型（string，与块类型不同！）**：另有接口返回 `table` / `board` / `timeline` / `calendar` 等字样（见 §7）。

**字段（列）类型（string）**：实测出现 `title` / `text` / `select` / `multi_select` / `date` / `id_number` / `url` / `created_at` 等。

> 注意一个**关键差异**：**块的 type 是数字，但字段类型和视图类型是字符串**。做数据模型时别混。

## 7 另一支接口里的对象类型（`/api/spaces/{id}/root` 等）

从空间/页面树接口里统计到的 string 型 `type`：`table` / `board` / `timeline` / `calendar`（视图）、`title` / `text` / `select` / `multi_select` / `date` / `id_number` / `url` / `created_at`（字段）、`user` / `space`（权限角色）、`emoji`（图标）、`group` /`filter`（视图分组与筛选）。

→ 这些直接喂给 **M0-T09（多维表模型）** 与 **M4**。

## 8 给 M2/M6/M7 的实现要求

1. **块表用「以 id 为键的对象」+ `parentId`/`subNodes`**，不要用嵌套数组——这是 FlowUs 的做法，也是同步时做增量 diff 的前提。
2. **块类型用数字**，并且**必须先把映射表定下来**（M0-T17）再动手写模型，否则会返工。
3. **正文放 `data.segments` 数组**（`{text, type, enhancer}`），行内样式放 `enhancer`——不要自己拍一套。
4. **每个块有 `version`**，同步时用它做冲突判定（M7-T04）。
5. **页面块 `type:0` 自带 icon/cover/description**，所以「页面图标」「封面」不是外挂属性，是页面块自身字段（呼应 M2-T11）。
6. **字段类型与视图类型是字符串**，与块的数字 type 分开建模。
