# M3-T01 临时签名取件码通道（签名接口部分）

> 方案 C（用户已定）：**服务端持密钥、签发有期限的 URL，App 直连对象存储取资源**，整个桶不对公网可读。
> 本文件只覆盖这一轮真正做完的部分（签名核心 + 校验闸门 + CLI），**真实链路仍未验证**，原因见 §5。

## 1 交付了什么

| 文件 | 作用 |
| --- | --- |
| `server/src/cloud/presign.ts`（新） | SigV4 **查询串签名**（presigned URL）。与 `store/r2Store.ts` 的头部签名分开实现：查询签名有 UNSIGNED-PAYLOAD、X-Amz-* 进 canonical query 等硬性差别 |
| `server/src/cloud/assetTicket.ts`（新） | 业务层：key 安全校验 → 账号 ID 校验 → 有效期夹紧 → 签发取件码（单个 / 批量） |
| `server/tests/presign.selftest.ts`（新） | 34 条断言：签名确定性、参数排序与编码、TTL 夹紧、路径穿越/白名单、主机名注入、批量语义 |
| `server/src/cli.ts` | 新增 `ticket --keys a,b [--ttl 300]`，可在服务器上一行命令签发并当场 curl 验证 |

## 2 关键设计点（都是踩过或想到的坑）

1. **TTL 必须夹紧**：`MAX_TTL_SEC = 3600`，默认 300 秒。太长等于把私有桶公开。
2. **key 是唯一入口闸门**：拒绝 `..`、空段、绝对路径、反斜杠、控制字符、超长；**只放行 `assets/`、`clips/` 两个前缀**
   （与 `store` 层的键规则一致）。没有这道闸门，取件码接口就是"桶内任意对象读取器"。
3. **账号 ID 必须校验成 32 位 hex**：它是要拼进主机名的，不校验就等于让调用方决定往哪台主机发请求（SSRF 面）。
4. **批量不做部分成功**：一批里有一个坏 key 就整批失败——避免调用方误以为"部分签发成功"而静默丢图。
5. **校验不依赖环境变量**：批量签发先校验完 key 再读 R2 配置。
   这条是自测抓出来的——原来先 `loadR2Config()`，结果少配一个环境变量会报"R2 环境变量未设置"，
   把一个明显的参数错误掩盖成配置错误。
6. **App 永远拿不到密钥**：URL 里只有 AccessKey **ID**（签名算法要求的公开部分），Secret 只在服务端内存里参与 HMAC。

## 3 签名正确性的证据（这条最要紧）

不靠"我觉得对"，用 **botocore（AWS 官方 SDK 内核，独立实现）作为离线判据**逐字节比对：

| 用例 | botocore 签名 | 我们 | 一致 |
| --- | --- | --- | --- |
| `assets/a1.png`，TTL 300，`2026-11-10T01:03:59Z` | `29d8e043c45c4a9b5ab71c859cf4ada00204e648100db53710298ddd3a417c4f` | 同值 | ✅ |
| `assets/中文-1.png`（**预编码路径**），TTL 300，`2026-11-10T01:04:28Z` | `a5ee3abe4d3bdf447ce86f0f9b79abb0f9d8df5e0d591d739f1c8584228e9da0` | 同值 | ✅ |

比对用**合成凭证**（`synth-access-key` / `synth-secret-key`），不涉及任何真实密钥；两边用同一个 `X-Amz-Date`
（先从 botocore 的 URL 里读出来，再用同一时刻复算我们这边），所以结果是确定的，不是"跑两次碰巧一样"。

### 一个刻意的差异（要写清楚，别以后被人当成 bug）

botocore 传**未编码的中文路径**时，S3 分支**不做路径规范化**（`S3SigV4Auth._normalize_url_path` 直接返回原样），
所以它签的是 `.../assets/中文-1.png` 的原始 UTF-8 字节；我们的实现会**先按 RFC3986 逐段编码再签**，
签的是 `.../assets/%E4%B8%AD%E6%96%87-1.png`。按 SigV4 规范，canonical URI 必须是"URI 编码后的绝对路径"，
而且 boto3 是在**调用签名之前**就把 key 编码好的 —— 所以我们与"boto3 实际会签的东西"一致（上表第二行就是证据）。
**结论：这不是 bug，是分工不同。**

### 为什么没有用 AWS 文档里的公开测试向量

试过，被两件事挡住：
1. 安全扫描会把文档示例里的 AccessKey 当"硬编码凭据"拦下来（它分不出那是公开示例）；
2. 本环境的占位替换会把这类值改写，落盘后就不是原值，无法当比对基准。

botocore 比对是更干净的替代：**同样的独立性，还不往仓库里放任何密钥形状的字符串**。

## 5 没做完的：真实链路（已拆成 M3-T09）

**这台机器上 R2 端点不可达**，所以"服务端真的接受这个签名""App 真能从 R2 取到字节"这两件事**没有验证**：

```
node … r2-probe → FAILED: fetch failed (ETIMEDOUT)
DNS r2.cloudflarestorage.com → 172.64.190.1 / 172.64.66.1 / …（被劫持成假域名）
curl 直连 → 000；curl --doh-url https://doh.pub/dns-query → 000
```

这与已知的本机网络问题一致（网关 DNS 污染，GitHub Releases 也踩过同样的坑）。凭证本身没问题
（`E:\credentials\r2.txt` 里账号 ID 是 32 位 hex、Secret 64 位，形状正确）。

→ 已把剩余部分拆成 **M3-T09**：在**服务器（腾讯云 VPS）上**跑 `cli ticket` + `curl -I` 取件码，
确认 200/206；再让客户端取一张真图落地。以及把签名接口挂成一个 HTTP 端点（当前只有 CLI 形态，
没有常驻 HTTP 服务——这一条也是 M3-T09 的一部分）。
