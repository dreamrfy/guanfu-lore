# 基准 · 编辑器内核像素对齐实测（M0-T12）

> **M0-T12 交付物 —— 这是可行性关卡，结论决定 M2 怎么走。**
> 实测日期：2026-11-10 ｜ 环境：Flutter 3.47.9 stable / Windows 11 / Visual Studio 2022 生成工具
> 证据：`docs/基准/证据/M0-T12/我们实现-编辑器渲染.png`（真实截图）｜ 对照工程：`tools/editor-spike/`

## 结论（先说）

**✅ 可以用 `appflowy_editor_ce`，不需要换内核、也不需要自研。**

理由（三条，都有实证）：
1. **它默认的行高就是 `1.5`** —— 正好等于 FlowUs 正文 16/24（=1.5）。这不是巧合方向上的错误，是**开局就对**。
2. **样式覆写入口齐全**：`EditorStyle` 暴露 `textStyleConfiguration`（可传任意 `TextStyle`，含 `height`）、`lineHeight`、`padding`、`maxWidth`、`cursorColor`、`selectionColor`、`textSpanDecorator`。
3. **一次真实渲染已验证**：按 FlowUs 实测数值渲染后，**字号与字形高度比例完全正确**（见下）。

**但有两个前提必须先补**（否则上手就会做偏）：
- ⚠️ **块间距（段落间距）我还没采** → 见第 4 节，已拆 **M0-T19**
- ⚠️ **标题要显式覆写**：它默认 `[32, 28, 24, 18, 18, 18]` + `FontWeight.bold`(w700)，而 FlowUs 是 **40 / 64 / w600**

## 1 内核默认值 vs FlowUs 实测（逐项对照）

| --- | --- | --- | --- | --- |
| 正文字号 | `16.0` | `16` | ✅ 一致 | — |
| **正文行高** | **`lineHeight = 1.5`** | **24 ÷ 16 = 1.5** | ✅ **一致** | 可，但不用改 |
| 正文字色 | `Colors.black` | `#37352F` | ❌ 要改 | ✅ |
| 加粗字重 | `FontWeight.bold`（**w700**） | 字重只用 **400/500/600** | ❌ 要改 | ✅ |
| 链接色 | `Colors.lightBlue` | 主色 `#0285FF` | ❌ 要改 | ✅ |
| 行内代码 | 红字 + 青底 | 待采（M0-T16） | ⏳ | ✅ |
| **标题字号** | **`[32, 28, 24, 18, 18, 18]`** | **大标题 40**、小标题 18 | ❌ 要改 | ✅（自定义 block builder） |
| **标题字重** | **`bold` = w700** | **w500 / w600** | ❌ 要改 | ✅ |

> 顺带发现：**当前 `client/lib/editor/flowus_editor.dart` 里的值全是拍脑袋的** ——
> `fontSize: 15, height: 1.7, color: #1F2329, bold: w700, href: #2B7CF6`，
> **没有一项对得上实测规格**（规格是 16 / 24 / `#37352F` / 400·500·600 / `#0285FF`）。
> 这就是「看着不对劲」的直接原因，不是内核不行。

## 3 一个必须写下来的技术限制（关系到"像素级"这个词）

实测日志：`Using the Impeller rendering backend (OpenGLESSDF)`。

**Flutter（Impeller/Skia）与浏览器（Chromium）是两个不同的渲染器**，字形的栅格化、字重描边、抗锯齿策略都不同。所以：

- **数值层面可以做到完全一致**（字号/行高/间距/颜色按规格写死）
- **像素层面做不到逐像素相同**，尤其是**文字的笔画粗细与边缘灰度**——同一个 40px 字，两个渲染器画出来的像素不会逐点相等

这与当初给用户的预告一致。**"像素级"的验收口径应当定为：布局与数值逐项一致 + 并排肉眼难辨**，而不是逐像素比对。这条建议已写入 M11 的验收口径。

## 4 这次实测**新暴露的缺口**（重要）

渲染出来发现：**两段正文之间相距 29px**，而我采到的行高规格是 **24px**。

原因不是内核错了——**是我采漏了「块间距」**：
- 我采的是**行内行高**（16/24 = 1.5），这个对上了
- 但**段落与段落之间的间距**（FlowUs 的块间距）**从没采过**

这类量在 M0 里属于"块级排版"，和行内行高是两回事。已拆 **M0-T19**：采齐 段落/标题/列表/引用 各块的**上下间距、内边距**，以及空块的高度。

> 这正是"先做可行性实测"的价值：**这个缺口不跑一次真渲染就发现不了**，等 M2 写完再发现就要返工。

## 5 给 M2 的行动清单

1. **保留 `appflowy_editor_ce`**，不换、不自研。
2. **重写 `_flowUsEditorStyle`** 的每一个值，全部改为实测值（现版本 5 个值全错，见第 1 节）。
3. **标题必须自定义 block builder**：40/64/w600（大）、18/19.8/w500（小），别用默认的 32/w700。
4. **等 M0-T19 的块间距出来后**再写段落间距，别先拍一个数。
5. **验收口径**按第 3 节：数值逐项一致 + 并排肉眼难辨；**不要承诺逐像素相同**。
6. 渲染后端固定在 Windows 上实测（Impeller），Web/安卓端表现另行验收（M10）。

## 6 复现方式

```bash
# 1) 工程在临时区（构建产物大，不入库）
cd /e/dev/tmp && flutter create --platforms=windows editor-spike
# 2) 用仓库里的两份文件覆盖（源码已入库，便于复现）
cp $REPO/tools/editor-spike/main.dart      editor-spike/lib/main.dart
cp $REPO/tools/editor-spike/pubspec.yaml   editor-spike/pubspec.yaml
# 3) 构建 + 跑 + 抓屏
cd editor-spike && flutter pub get && flutter build windows --release --no-tree-shake-icons
./build/windows/x64/runner/Release/editor_spike.exe
```
