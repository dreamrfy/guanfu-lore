# 剪藏链路说明（把"剪藏"这件事一次讲清）

> 2026-11-13 · 起因：用户对"剪藏到底在哪台机器上跑"理解有偏差，这里把链路、数据流向、每个部件归谁管一次写清。

## 0. 一句话

**剪藏 = 把外部内容（公众号文章、B站视频、网页）抓下来、存成一份自己的副本（原文 HTML + 图片），放进你的库。**
重点在"**自己的副本**"：对方删文、图片 CDN 失效，你的库里还在。

## 1. 三条入口（谁负责"抓"）

| 入口 | 触发动作 | 谁去抓 | 需要谁在公网上 |
| --- | --- | --- | --- |
| ① 微信客服转发 | 手机把文章转发给"微信客服" | **服务器**每 5 分钟轮询微信接口取消息 | 不需要（轮询，不是回调） |
| ② 粘贴链接 | 在网页端/桌面端粘贴 URL 点"剪藏" | **剪藏服务**（`server/src/clipServer.ts`，本次新写） | 需要（手机/扩展要能访问它） |
| ③ 浏览器扩展 / 网页划线 | 扩展里点"剪藏" | 扩展直接调同一个剪藏接口 | 需要（同 ②） |

**① 已经在线上跑着**：`bijiapp-poll.timer`（每 5 分钟）→ `bijiapp-poll.service` → 拉消息 → 抓正文 → 下载图片 → 写 R2。桶 `bijiapp-assets` 现有 clips/ 110 个对象、assets/ 110 个。

**② 这次新写的剪藏 HTTP 接口还没部署**（服务器上目前只监听 SSH 20001，没有对外的剪藏服务，也没有域名/反代）。

## 2. 数据放在哪

```
       微信客服消息                粘贴链接 / 扩展
            │                          │
            ▼                          ▼
      ┌──────────────────────────────────────┐
      │  剪藏服务（server/，Node 24）          │  ← 唯一"抓取器"
      │  · 安全 HTTP 层（协议/主机白名单/SSRF 防护）│
      │  · HTML 白名单清洗 + 正文抽取            │
      │  · 图片下载（魔数校验）+ 快照生成         │
      └───────────────┬──────────────────────┘
                      ▼
        R2（对象存储，私有桶）: clips/*.json + assets/*
                      ▲
                      │  只发"临时取件码"（签名 URL，5 分钟过期）
        ┌─────────────┴─────────────┐
        │                           │
   客户端本地库                   云端 API（待建）
   （网页/手机/桌面各一份）        （拉列表、读正文）
```

- **原文和图片只存在服务器（R2）**，客户端不长期持有副本，只在打开时通过"取件码"临时读取。
- **客户端本地库（IndexedDB）= 缓存 + 离线队列**：网页/桌面端现在把数据存在本机（这是现状，不是最终形态）。

## 3. "多端同步"是什么意思

**不是客户端之间互传，而是所有客户端都跟服务器对齐。**
手机转发进库 → 网页端刷新就能看到；网页端剪藏 → 手机端也能看到。服务器是唯一事实源。

桌面版装好后，你电脑上那份本地库同样只是"客户端之一"，联网时和服务端对齐。

## 4. 三个部件各归谁管

| 部件 | 跑在哪 | 谁负责 |
| --- | --- | --- |
| 抓取（剪藏服务 + 轮询） | 云端 VPS（也可在桌面端自带的 sidecar 里） | 服务端 `server/` |
| 存储（正文/图片/快照） | R2 私有桶 + 服务端 SQLite | 服务端 |
| 界面（编辑、表格、搜索、AI） | 网页端 `app/`（Tauri 桌面壳 = 同一个网页端 + 壳） | 客户端 |
| 同步（推拉、冲突） | 服务端 API（**尚未存在**） | 双方 |

## 5. 因此，桌面版要不要"自带剪藏服务"？

- 自带：桌面端不依赖云端可达性，断网也能剪；代价是**出现第二套抓取器**（桌面一份、服务器一份），同一篇文章在两边剪可能存两份、行为也会分叉。
- 不自带：桌面端只是"壳 + 客户端"，剪藏一律走服务器；**只有一套抓取器**，维护成本最低。
- 关键事实：**① 微信转发那条路无法搬到桌面端**（微信客服消息只能在服务器上轮询），所以服务器无论如何都要存在。既然如此，"剪藏抓取器"只有一份会更可持续。
- 结论：**桌面版不自带剪藏服务，走服务器**（D1 = B，服务器为准）。
  - 代价：断网时桌面端不能剪藏（但能编辑本地已缓存的内容）。
