# V3.2 部件级开源选型报告（2026-11-12）

> 本报告响应两项任务：① 「不重复造轮子」铁律落盘（已写入全局记忆）；
> ② 确认真实产品需要的部件清单 + 每个部件的开源替代评估。
> 用户需求定版（8 轮问答确认）：交互逻辑/操作习惯/页面布局对齐 FlowUs；
> 字体图标用开源可切换；三大核心 = 块编辑器 + 互联网剪藏 + AI Agent（可挂 skill/MCP）；
> 三端（Windows 桌面 + 手机 + 网页）；单人优先、预留 ≤10 人协作；
> 核心数据自托管（VPS + R2）；存量代码不预设权重，客观对比。

## 一、现有开发需求文档与开发清单的问题（任务 2.1 答案）

### 问题 1：任务表按「模块」组织，掩盖了「部件」属性
V3.0 任务表 M0~M12 是按**功能模块**切的（M2 编辑器、M4 表格、M3 剪藏…），
每个任务默认「自己实现」。没有一层「这个模块内部哪些是自研、哪些该用现成件」的决策记录。
结果：编辑器内核选了开源（appflowy_editor_ce，做对了），但**同一时期**的
字体切换（6 档主题表）和图标库（105 图标 × 4 套导出管线）自己造了管线，
而这两个恰恰是开源界最成熟的领域（开源字体栈 + 图标库全家桶）。

### 问题 2：「像素级 1:1」目标与「用开源件」内在冲突，未及早暴露
像素对齐 FlowUs 意味着每个部件都要「照着 FlowUs 重做」——这本身就是一种造轮子。
V3.1 用户已把目标改为「操作逻辑/布局对齐，视觉资产可换」，冲突已解除，
但任务表 M2 剩余任务（T04/T09/T10/T17/T19/T25…）仍按「照抄 FlowUs 规格」写，
需要按新目标重述。

### 问题 3：AI 模块按「功能」设计，没按「Agent 架构」设计
M9 重定义后是「供应商入口 + 调用层 + 选区工具条 + 整篇工具条」，
本质是「把 AI 当 API 用」。而用户真实需求是 **Agent 级**：可挂 skill、可挂 MCP、
可自定义供应商——这是另一个量级的架构（工具调用循环、上下文管理、权限），
现任务表没有体现，需要重写。

### 问题 4：没有「部件清单」这一层
从需求到任务之间缺一份《部件清单》：产品 = 哪些部件 × 每个部件选型结论 ×
自研理由（必须写明为什么开源件不满足）。有了它，「不重复造轮子」才能被审计。
本报告第四节就是这份清单的 v1。

## 二、大底座调研结论（AppFlowy / AFFiNE / 思源）

调研结论先说：**三个大底座都不能直接满足你的需求**，理由如下（有据可查）：

| 维度 | AppFlowy | AFFiNE | 思源 SiYuan |
| --- | --- | --- | --- |
| 技术栈 | Flutter + Rust | React + Node.js（BlockSuite 编辑器） | TS + Electron（自研内核） |
| 桌面 | ✅ 强（主战场） | ✅ 可用 | ✅ 强 |
| 网页版 | ⚠️ 弱（社区反馈 web 端问题多，2026-04 YunoHost 论坛列了 web 不工作等 9 项问题） | ✅ 强（网页优先设计） | ⚠️ 无真正网页版（Docker 托管后仍偏桌面形态） |
| 手机 | ✅ 有但评分一般（Google Play 3.9） | ⚠️ 移动端长期 beta | ✅ 有（体验中规中矩） |
| 多维表 | ✅ 网格/看板/日历 | ✅ 数据库视图 | ⚠️ 属性面板较基础 |
| 自托管 | ⚠️ **开源但限制多**：Reddit 实测报告自托管限 2 用户、AI 上锁，被批「不是真开源」；**其商业云也跑在同一代码上，功能对齐受商业策略约束** | ⚠️ 自托管免费限 10 席位、AI 部分付费（Enterprise Edition 许可证，2026-10 官方页明示） | ⚠️ 本体 AGPL 全功能免费，但同步/备份接口需付费订阅，且历史上有「S3 同步要登录账号」的争议（issue #8835） |
| AI | 有 AI 集成（部分收费） | 自带 AI（付费墙内） | 较弱，靠插件 |
| 界面对齐 FlowUs | ⚠️ 是自己的设计语言，改成 FlowUs 的操作逻辑 = 大规模改造 | ⚠️ 同左（且白板混排设计更远） | ⚠️ 偏传统文档风 |

**核心判断**：你的硬约束是「操作习惯与 FlowUs 一致 + 核心数据自托管不受限 + AI 可挂 skill/MCP」。
- 大底座自带 UI/交互是它们自己的，改造成 FlowUs 的交互逻辑 ≈ 重写 UI 层，工作量不小于自研，还背上了对齐上游版本的长期负担；
- 自托管限制（席位/AI 锁）与「核心数据自托管不受限」冲突；
- AI 均不能挂 skill/MCP（思源有社区 MCP 插件是反向的：让外部 AI 操作思源，不是产品内 Agent）。

→ **大底座作为「整体替换」路线不推荐**。但它们的**编辑器/表格子件**值得单独评估（见下节）。

## 三、部件级开源件调研（每个部件：现成方案 → 结论）

### 3.1 编辑器（已用开源，维持）
- **现方案**：`appflowy_editor_ce`（pub.dev，AppFlowy 官方独立包，活跃维护）✅
- **替代考察**：BlockSuite（AFFiNE 的编辑器，可独立用但 React 系，与 Flutter 客户端不兼容）、
  Flutter Quill、Super Editor。
- **结论**：**继续用 appflowy_editor_ce**。它已是「编辑器部件级的开源选择」，
  当初选型是对的。要补的不是换内核，而是把 FlowUs 交互规格（斜杠菜单/块手柄/拖拽）
  作为它的**插件式扩展**来做（它本来就支持 builder/customize）。

### 3.2 字体切换（自研过重 → 换开源方案）
- 已造的：6 档主题表 + GB2312 子集管线（M12-T02）。
- 开源界成熟做法：直接打包开源字体家族（Noto Sans SC / 霞鹜文楷 LXGW WenKai / 思源宋体）
  + 用社区现成的子集工具（如 `fonttools` pyftsubset 命令行，本身就是开源工具链）。
- **结论**：字体文件全部用开源字体（授权无顾虑），**子集管线若已有脚本就保留**（纯工具，不算造轮子），
  6 档主题表是产品功能（用户可切换字体=你的需求），保留但候选字体全换开源。
  ⚠️ 待办：检查 M12-T02 是否打包了非开源字体进 exe（微软雅黑/等线/楷体/宋体是 Windows 系统字体，
  **不能打包分发**，只能「引用系统已装的」——需要确认实现方式）。

### 3.3 图标库（已转向开源，收尾即可）
- M12-T03 已选 MingCute/Lucide/Phosphor 三档（Apache-2.0/ISC/MIT）✅ 方向已对。
- **遗留**：① 工作区有 3 行依赖未提交；② `assets/icons/legacy/` 的 FlowUs 仿制 96 个图标待你确认后彻底删除（版权风险）。
- **结论**：不用再做什么选型，收尾即可。

### 3.4 剪藏（服务端原型保留 + 两个部件换开源思路）
- 已有：企业微信客服链路（真实冒烟通过）——这是**你自己的业务通道**，属于「必须自研/自配置」的部分，保留。
- **公众号批量获取**：开源 `wechat-article-exporter`（8.3K star，支持 Docker/Cloudflare 部署、批量导出）
  可作为「历史号文章批量导入」的补充通道——比自研轮询强得多，可直接部署在你 VPS/R2 上。
- **网页通用剪藏**：Obsidian Web Clipper（开源，MIT，官方仓库 obsidianmd/obsidian-clipper）
  是当前最强开源网页剪藏器（支持智能提取/Interpreter AI 增强）。**建议直接采纳其「浏览器扩展→HTTP→服务端」的模式**，
  甚至可 fork 它把保存目标指向你的服务端，替代自研浏览器端。
- 小红书/B站/抖音：无单一开源件通吃；B站/抖音视频信息抓取有成熟开源库（yt-dlp 系、bilibili-API-collect）可引入。
- **结论**：通道保留，**前端采集与公众号批量部分引入现成开源件**，把自研范围缩到「你特有的转发链路 + 入库规范」。

### 3.5 多维表引擎（自研中 → 评估引入开源内核）
- 已自研：`flowus_table.dart`（19 字段类型/7 视图/筛选排序）。
- 开源替代：APITable（AGPL，canvas 渲染，协作架构）、Teable、NocoDB（偏 B 端，重）。
  它们都是**完整产品**而非嵌入库，塞进 Flutter 客户端不现实（web 嵌入则破坏桌面体验）。
- **结论**：这是目前**最难找到「可直接嵌入的开源件」**的部件——Notion 系产品都把它当核心资产。
  现有自研引擎已按 FlowUs 数据结构对齐且 434 测试在跑，**建议保留自研**，
  但把「视图渲染」继续做薄（表格 UI 组件在 Flutter 生态也有现成的，如 syncfusion_flutter_datagrid 社区版可评估）。
  这是少数「自研有充分理由」的部件——理由写进部件清单。

### 3.6 同步与存储（未开始 → 直接用开源方案）
- 需求：三端同步、核心数据在 VPS+R2。
- 开源现成方案：**不自己写同步引擎**。候选：
  - 思源模式：S3/WebDAV 同步（但其接口绑定订阅，见上表）——不引入；
  - **R2 直连**：R2 兼容 S3 API，客户端用现成 S3 客户端库 + 冲突解决用 CRDT 库（Flutter 生态有 `cross_file`/Yjs 的 Dart 移植 `ydart` 等可评估）；
  - 桌面优先阶段可先用「SQLite WAL + 对象存储快照」这种最简模式（现有 db_backup_test 已有雏形）。
- **结论**：同步架构设计时以「对象存储 + CRDT/快照」为基准，组件全用开源库，不自研同步协议。

### 3.7 AI Agent 层（未开始 → 全部用开源件拼装）
这是「一切皆插件」的主战场，全部有开源现成件：
- **MCP 客户端**：官方 `modelcontextprotocol` 有 TS/Python SDK；Dart 侧有社区 `mcp_dart`/`dart_mcp` 可评估，或在服务端(Node)侧做 MCP 桥（服务端本来就是 Node 24）→ **零自研**。
- **供应商网关**：`one-api`/`new-api`（开源，聚合国内大厂 API，OpenAI 兼容格式）部署在你 VPS 上，App 只对一个兼容端点说话 → **零自研**。
- **Agent 循环/工具调用**：LangChain.js / Vercel AI SDK（服务端）现成；skill 体系可直接采纳 **Anthropic Agent Skills 开放格式**（Markdown+frontmatter，已有大量社区 skill）。
- **结论**：AI 层 = one-api（供应商）+ MCP SDK（工具）+ Agent Skills（技能）+ 现成 Agent 框架（循环）。
  **自研范围只剩「把这些接进编辑器 UI 的那一层」**。

### 3.8 导入导出（部分已做）
- Markdown 导出已自研（简单，保留）；HTML/PDF 打印用系统/浏览器能力；整库导出=SQLite 文件+附件打包（简单）。
- **结论**：无重造轮子问题，维持。

### 3.9 视觉资产（图标/字体/主题）
- 已按开源三档落地（见 3.2/3.3）。主题系统是 Flutter 原生能力，不算造轮子。
- **结论**：维持，收尾 legacy 图标删除。

## 五、总体建议（供拍板）

**推荐路线：维持现有 Flutter 客户端 + Node 服务端的架构，按第三节逐部件执行「开源替换/引入」，
废弃 V3.0 任务表中「照抄 FlowUs」式的自研任务，改按部件清单重排任务表（V3.2）。**

理由：
1. 架构不用推翻（推翻重来的主要是 M2 剩余的「照抄式」任务，沉没成本本来就不大）；
2. 你的差异化本体（交互对齐 FlowUs、企业微信通道）恰好是开源界没有的部分，自研集中在这几块是合理的；
3. AI/同步/剪藏采集三个原本要大量自研的领域，现在全部有成熟开源件，工作量大幅下降；
4. 三端中桌面最强（Flutter 主场），网页版是现有架构的最大短板（Flutter web 性能一般）——
   这一点如实告知：如果将来网页版体验不满意，备选是把服务端做成标准 API + 单独的 React 网页前端（复用 BlockSuite），届时再决策，不影响现在的路线。

**下一步（待你拍板后执行）**：
1. 按本报告第四节把任务表重排为 V3.2（部件清单驱动，每项标「开源件/自研+理由」）；
2. 收尾三件小事：提交 pubspec 依赖、删 legacy 图标（待你确认）、核对字体打包合规；
3. M2R-T01（页面树接真实库）按新路线继续——它不受本次调整影响。

## 六、补充调研（2026-11-12 第二轮）：「可直接部署、不写代码」的开源编辑器成品

> 起因：用户对自研编辑器进度感到恐惧（「一写代码就错」「进度为 0」），追问是否有
> Docker 一键部署、拿来就用的开源编辑器。本轮专门查证，结论如下。

### 6.1 能直接 Docker 部署的成品（今天就能用，零代码）

| 项目 | 部署 | 编辑器 | 多维表 | 硬伤 |
| --- | --- | --- | --- | --- |
| **AFFiNE** | Docker Compose 官方支持 | ✅ 块式，Notion 同源交互（斜杠菜单/页面树/多维表/白板） | ✅ 有 | 自托管限 10 席位（单人够用）、AI 部分付费（可不用它的 AI）、手机端 beta |
| **思源 SiYuan** | Docker 可浏览器访问 + 桌面/手机 App | ✅ 块式，中文生态最好 | ⚠️ 属性面板较基础 | 界面风格偏传统（非 FlowUs/Notion 风）；官方 S3 同步接口要订阅（数据本身全本地免费）；AI 靠插件 |
| **Docmost** | Docker Compose 一键，社区口碑最好的新手友好项 | ✅ 块式（表格/代码块/callout/Mermaid） | ❌ **没有数据库/多维表**（Reddit 用户实测确认） | 团队 wiki 定位，无多维表 = 缺你第二核心需求 |
| AppFlowy | 桌面 App 为主 | ✅ | ✅ | 自托管限 2 用户、AI 锁；启动崩溃等桌面 bug 报告仍多（issue #8332 等） |

### 6.2 Typora 类（澄清）

Typora 本身**闭源收费**（$15/89 元），不是开源。开源同类（MarkText/Zettlr/Ghostwriter）
全是**纯 Markdown 编辑器**：没有块式结构、没有页面树/多维表、没有剪藏和 AI 的容身之处，
满足不了三大核心需求，仅适合「写纯文档」场景。

### 6.3 关键澄清：自研的到底是什么

- **编辑器内核不是自研**——一直是开源的 `appflowy_editor_ce`。
- 自研/在写的是：内核之上的 FlowUs 式交互层（斜杠菜单/块菜单/拖拽）、页面树、多维表引擎。
- 进度事实：内核已跑通、斜杠菜单/块菜单/颜色面板/代码块/Markdown 快捷/拖拽有实现+测试，
  全量 434 测试；但**块类型覆盖不全、页面树未接真实库（M2R 8 项全 TODO）**——
  用户验收「什么都没有」的直接原因就是 M2R 未做，观感上=进度 0。

### 6.4 第二轮结论：给用户的三层选择

- **层 1（零代码，今天可用）**：Docker 部署 AFFiNE 或思源当日常工具。
  代价：交互/外观不是 FlowUs 定制版，剪藏/AI 要用它们自带生态而非我们规划的产品形态。
- **层 2（换赛道，编辑器组件最成熟）**：放弃 Flutter 客户端，改 React 生态
  （编辑器用 BlockNote/BlockSuite/Tiptap —— Notion 风格开源组件，生态远比 Flutter 成熟），
  服务端仍自托管。代价：现有客户端作废，重写外壳/表格；但每个部件都有更多现成件可选，
  网页版天然解决。多维表仍无嵌入式现成件（Teable/APITable 是独立产品不是组件）。
- **层 3（维持现路线）**：继续 Flutter + appflowy_editor_ce，先补 M2R（页面树接真库）
  让「能用的感觉」尽快出现。代价：编辑器交互层继续自研，三端中网页版最弱。

**修改后的推荐**：先做**层 1 的试装**（一天内完成、零代码、可逆）——把 AFFiNE 和思源
都部署到 VPS，用户真实使用一周；期间继续层 3 的 M2R-T01（不受影响、代码不白写）。
一周后拿真实体验拍板层 2 还是层 3。**在试装结论出来前，不做层 2/层 3 的大投入决策。**
这符合「先查证再动手」铁律：先验证现成品够不够用，再决定要不要继续造。
