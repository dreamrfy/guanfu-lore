# 同步层（D4）与 RAG（D5）实施设计

> 2026-11-13 · 依据 9.9 的决策写成"可直接开工"的规格，方便下一批直接实现，也方便审查。

## 一、同步层（D4：服务器为准 + 离线队列 + 冲突副本）

### 1.1 角色与总原则

- **服务器是唯一事实源**：所有内容（页面、剪藏记录、属性）先写服务器。
- **客户端是缓存 + 队列**：本地 IndexedDB 存一份（读快、离线可用）；联网时把本地改动推上去。
- **冲突不静默丢弃**：同一处被两台设备改过 → 服务器版本照用，本地版本另存为「冲突副本」，用户自己挑。

### 1.2 服务端要加的东西

1. **表 `sync_state`**（每张表的元信息）：
   | 字段 | 说明 |
   | --- | --- |
   | `entity` | 表名（pages / collection_records / ...） |
   | `seq` | 单调递增的变更序号（全局一张 `change_log` 表更好，见下） |
   | `updated_at` | 毫秒时间戳 |

2. **表 `change_log`**（变更流水，也是推送的来源）：
   | 字段 | 说明 |
   | --- | --- |
   | `seq` | 自增主键，客户端的「拉取游标」 |
   | `entity` / `entity_id` | 改的是哪张表的哪一行 |
   | `op` | upsert / delete |
   | `payload` | 该行的完整 JSON（简单可靠，代价是体积） |
   | `actor` | 哪台设备改的（冲突判定要靠它） |
   | `base_seq` | 改这行时，客户端看到的版本号（= 乐观锁） |

3. **接口**（`server/src/cloud/sync.ts`，挂在剪藏服务同一进程里）：
   | 方法 | 作用 |
   | --- | --- |
   | `GET /api/sync/pull?since=<seq>&limit=200` | 拉客户端没见过的变更（按 seq 递增） |
   | `POST /api/sync/push` | 推本地改动：`{entity, entityId, baseSeq, payload, op}`；服务端用 `baseSeq` 判冲突 |
   | `POST /api/sync/conflicts` | 交回冲突副本（服务端已存下来的本地版本） |

4. **冲突判定（服务端）**：
   - 推送时 `baseSeq < 该行当前 seq` → 有人改过 → **不覆盖**；
   - 服务端把「客户端推来的版本」存成冲突副本（`conflicts` 表：原行 id + 客户端版本 + 时间 + 设备名），并把客户端那次的 seq 记下来；
   - 响应里告诉客户端「这行有冲突，副本已存」。

### 1.3 客户端要加的东西

1. **本地队列**（IndexedDB 新表 `outbox`）：每次本地改动先写队列（带 `baseSeq`），再后台推送。
2. **推送器**（`app/src/data/sync.ts`）：联网时按序推送；失败保留在队列并退避重试。
3. **拉取器**：定时/手动 `pull`，把新变更合并进本地库，并更新游标。
4. **冲突副本的展示**：记录页/页面底部显示「有 1 个冲突副本」，点开可对比、可选择采用哪个。

### 1.4 AI 冲突辅助（用户提出，排在这层之后）

在同步层之上加一层"AI 帮忙判断"：

1. **高亮冲突**：把服务器版本与冲突副本的差异块高亮（用现成的 diff 库或自己按块比对）。
2. **AI 判断位置**：
   - 冲突内容**不在同一位置**（改的是不同段落/不同块）→ **直接合并进云端最新**（服务器版本为主体，把另一台的改动并进去）；
   - **在同一位置**（同一段/同一句）→ **继续保留为副本**，不自动覆盖，交给你挑。
3. 落地方式：把「两个版本的块序列 + 差异摘要」发给模型，让它输出"可合并/需人工"的判定 + 合并后的块序列；
   再由同步层按判定写入。**模型只给建议，最终落库要走确定性逻辑**（同一位置绝不自动覆盖）。

### 1.5 分期

| 期 | 内容 | 估计 |
| --- | --- | --- |
| S1 | 服务端 `change_log` + pull/push 接口 + 冲突副本存储 | 2–3 天 |
| S2 | 客户端 outbox + 推送/拉取 + 冲突副本展示 | 2–3 天 |
| S3 | AI 冲突辅助（高亮 + 判定 + 合并） | 2 天 |

## 二、RAG（D5：BM25 + 云端向量混合，直接做 B 最小版）

### 2.1 为什么不是"先 A 后 B"

A（关键词）是 B 的一个零件（混合检索里的一路）。分两轮等于做两遍，所以直接做 B。

### 2.2 选型

| 环节 | 选择 | 理由 |
| --- | --- | --- |
| embedding | **硅基流动 bge-m3**（国内直连、中文好、有免费额度） | 正文允许出本机（用户已确认）；可换 OpenAI / 本地 Ollama |
| 向量存储 | **SQLite 一张表**（`vec_id, entity, entity_id, dim, vec BLOB`），查询时算余弦 | 当前规模（几十~几百篇）不需要专门的向量库；先用最笨的办法把链路跑通 |
| 关键词一路 | **BM25**（自写或引 `bm25s`/`rank-bm25`） | 中文字段切分要先做（jieba 或按字bigram），否则中文 BM25 效果差 |
| 融合 | **RRF**（两路结果的排名倒数加权） | 不用调权重参数，比"分数加权"稳 |
| 索引时机 | 正文变更后异步重算该块的 embedding | 增量索引，不全量重建 |

### 2.3 数据流

```
页面/记录正文变化 → 切块（按块，保留标题层级）
                  → BM25 索引（本地 SQLite FTS5 或自写倒排）
                  → embedding（云端 bge-m3）→ 向量表
问一句话 → 两路检索各取 top-20 → RRF 融合 → 取 top-5 片段
        → 组装 prompt（带出处：页面标题 + 片段 + 原文块 id）
        → 模型回答（严格模式：检索不到就回答"没找到"）
        → 出处渲染成卡片（可点击跳到原文那块）
```

### 2.4 与已有能力的衔接

- 出处卡片：`editor` 里已有"引用"样式（引用段落），AI 出处用同一套；
- "跳到原文那块"：已有 `setPendingBlockFocus`（搜索结果跳转用），AI 出处复用；
- 严格/宽松开关：D7 的设置项，检索为空时决定"回答没找到"还是"猜测并标注"。

### 2.5 分期

| 期 | 内容 | 估计 |
| --- | --- | --- |
| R1 | 中文切块 + BM25 一路（本地、零成本）+ 引用溯源 | 1–2 天 |
| R2 | embedding + 向量表 + RRF 混合 | 2 天 |
| R3 | 严格/宽松 + 出处卡片 + 跳转原文 | 1 天 |
