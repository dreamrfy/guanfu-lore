## 0. 一句话结论

**三条路径都能进，而且都不需要微信点头**——安卓的「分享 / 打开方式」列表是**能力匹配**，谁在安装清单里挂了对应的牌子，谁就出现在列表里。
真正拉开差距的不是「进不进得去」，而是**进去以后拿到的是什么**：两条给的是**文章网址**，一条给的是**聊天记录压缩包**。

**决定（2026-11-14 用户拍板）：② 和 ③ 一起做，列为最高优先级；① 搁置，等真正需要「整段聊天」或「文章已被删除」时再做。**

## 1. 先讲清楚「能不能进」这件事

安卓的「分享 / 打开方式」列表不是谁审核出来的名单。系统拿着一件「要处理的东西」去问所有装了牌子的 App：「这件东西你能接吗？」——谁挂了对应的牌子，谁就出现在列表里。

牌子的正式名字叫 **intent-filter**，写在 App 的安装清单（`AndroidManifest.xml`）里。挂一次，永久生效，不需要注册、不需要审核、不需要任何合作。

实测那天，微信那个面板里出现的第三方应用有：**AutoClaw**（`com.zai.autoclaw`）、**Chrome**（`com.android.chrome`）、**Edge**（`com.microsoft.emmx`）、**Alibaba.com**（`com.alibaba.intl.android.apps.poseidon`）等；系统 chooser 那一侧是另一批名单（微信、短信、QQ、Via、简阅·搜索、问小爱……）。**它们都不是微信的合作伙伴。**

> **关键区分**：列表由**谁画**，决定了它有多稳。
> - 微信**自己画的**面板（路径 ②）：微信自家的界面，规则它想改就改。
> - **系统画的** chooser（路径 ①③）：安卓的公共机制（`com.android.intentresolver/.ChooserActivity`），微信改不了。

## 2. 三条路径实证

### 路径 ①：转发 → 选择聊天 → 其他应用 → 转到其他应用 → 选择手机中的应用

| 项 | 值 |
| --- | --- |
| 谁画列表 | **系统** chooser（`com.android.intentresolver/.ChooserActivity`，标题「分享」） |
| action | ⚠️ 推断为 `android.intent.action.SEND`（包在系统 `CHOOSER` 里）——与 ③ 同类，但**未取到日志** |
| 载荷 | **一个文件**：`聊天记录_20261114_170103.zip`（预览框画的是文件图标 + 文件名） |
| 列表内容 | 首屏看到：快速分享、QQ、SukiSU、用 Tabbit 聊天（**列表是分页的，首屏不等于全部**，别拿它下结论） |
| 用户点几下 | 3 下（转发菜单 → 其他应用 → chooser 里选） |
| 证据级别 | ⚠️ **推断**，依据**只有预览框**（文件图标 + `.zip` 文件名）。**未取到原始事件日志行**——日志缓冲已经翻过去了（最早只留到 17:10，而这是 17:01 的事） |

**为什么说它是文件**：**只看预览框。**同一个 chooser、同一个「分享」标题，路径 ③ 的预览框是一行**文字 + 复制按钮**，路径 ① 的预览框是一个**文件图标 + 文件名**。这个渲染差别来自载荷本身（文件走 `EXTRA_STREAM`/文件 URI，文字走 `EXTRA_TEXT`），是**直接证据**。

**载荷是什么东西**：「聊天记录」是微信的**导出聊天记录**功能，它把一段聊天打成一个 zip 交给别的 App。所以这条路径给的不是「这篇文章」，而是「包含这篇文章的那段聊天」。（zip 内部结构**尚未查看**，见 §8。）

> 🔴 **一个被推翻的推论，留在这里防止重犯**：我一开始用「网格里有没有微信/短信」来反推载荷类型（以为它们只吃文本）。**这个推论是错的。**实测 `dumpsys package`：
> - 微信（`com.tencent.mm`）的 `SEND` 声明了 `image` / `video` / `text`（基础类型，即 `image/*`、`video/*`、`text/*`）；
> - 短信（`com.android.mms`）更宽，还声明了 `audio`、`application/ogg`、`text/x-vcard`；
> - 而 `cmd package query-activities -a android.intent.action.SEND -t application/zip` 实测有 **53 个目标，微信在里面**。
>
> 也就是说**微信本来就能收 zip**，用「它在不在网格里」判断载荷类型是无效的；更何况 chooser 的应用网格是**分页的**，首屏没有 ≠ 没有。**判断载荷类型只能看预览框，或者去抓 `wm_create_activity` 事件日志。**

> ⚠️ **调研方法上的坑（我踩过，接手的人注意）**：`dumpsys package` 打出来的 resolver table 是**按 scheme 与 type 分组**的，同一个组件会出现**很多次**。我第一次只读了前 12 行，就得出「AutoClaw 没有 `VIEW http`」的错误结论，后来被事件日志推翻。**要看某个组件到底声明了什么，必须把它的所有分组都读全，或者直接看事件日志里系统实际发的是什么。**

## 3. 三条对账

| | 路径 ① | 路径 ② | 路径 ③ |
| --- | --- | --- | --- |
| 入口路径 | 转发 → 选择聊天 → 其他应用 | 更多打开方式 → 点应用 | 更多打开方式 → 选择手机中的应用 |
| 谁画列表 | 系统 chooser | **微信自己的面板** | 系统 chooser |
| action | 推断 `SEND`（chooser 内） | `VIEW` ✅ | `SEND` ✅ |
| type | 文件类型 | 空 ✅ | `text/plain` ✅ |
| data | 文件 URI | `https://mp.weixin.qq.com/...` ✅ | 空（在 `EXTRA_TEXT`）✅ |
| **我们拿到** | **`聊天记录_*.zip`** | **文章网址** | **文章网址** |
| 拿到后要做什么 | 解开微信聊天记录导出格式 | 直接抓这个网址 | 直接抓这个网址 |
| 用户点几下 | 3 | **1** | 2 |
| 证据级别 | ⚠️ 推断 | ✅ 实证 | ✅ 实证 |

**要点**：路径 ② 和 ③ 交给我们的**是同一个东西——文章网址**，只是动作不同，所以两次列出的应用名单不一样。只有路径 ① 交给我们的是聊天记录 zip，那是微信的「导出聊天记录」功能，和文章本身没关系。

## 4. 实现难度与优劣

对着现有工程说：**②③ 拿到的都是网址 → 你已经建好的服务器抓取链路（`POST /api/clip`，见《剪藏链路说明》）原样能用，抓取逻辑一行都不用新写**，安卓壳只需要「接住意图 → 把网址转过去」。

| | 难度 | 优点 | 缺点 / 代价 |
| --- | --- | --- | --- |
| ② | ★ 最容易 | 用户最省事（1 下）；网址直达 | 列表是**微信自己画的**，微信改规则就掉出去；挂了「打开链接」的牌子后，用户点**任何**链接都会看到我们，必须做「非目标站点就转交浏览器」的兜底 |
| ③ | ★ 最容易 | 列表是**系统画的**，微信改不了，更稳；不限于微信——别的 App 分享一段带链接的文字也能进来 | 比 ② 多一步；挂了「接收文本」牌子后会出现在**所有**分享纯文本的清单里 |
| ① | ★★★ 最麻烦 | **唯一**能拿到整段聊天 / 多篇文章的入口；也是**唯一**在文章已被删除、拿不到网址时仍有内容的入口（包里是渲染好的内容） | 用户要 3 下；要多养一个 zip 解析器；若用 `*/*` 收文件，会被塞进所有分享清单 |

**三者挂的牌子互不冲突，可以一起挂**——App 装一次，三个入口同时都有。

---

## 5. 决定（2026-11-14 用户拍板）

- **② 和 ③ 一起做，列为最高优先级。**理由：两者几乎是同一件事（都是「拿到网址 → 走现有抓取」），成本极低，还能互相兜底。
- **① 搁置。**等真的需要「整段聊天」或「文章被删」的场景再补，届时需要先看清 zip 内部结构再估工。
- 命名上注意：本文的「三条路径」指**微信界面上把文章交给别的 App 的三条操作路径**，与《剪藏链路说明》里那个「四条入口（谁负责抓）」是**两个不同的轴**，别混。

## 6. 安卓端要写的东西（施工要求）

### 6.1 安装清单要挂的牌子

**路径 ②（浏览器式）：**

```xml
<intent-filter>
  <action android:name="android.intent.action.VIEW"/>
  <category android:name="android.intent.category.DEFAULT"/>
  <category android:name="android.intent.category.BROWSABLE"/>
  <data android:scheme="https"/>
  <data android:scheme="http"/>
</intent-filter>
```

**路径 ③（接收文本）：**

```xml
<intent-filter>
  <action android:name="android.intent.action.SEND"/>
  <category android:name="android.intent.category.DEFAULT"/>
  <data android:mimeType="text/plain"/>
</intent-filter>
```

**路径 ①（收文件，暂不做）：** `SEND` + 文件类型。具体 MIME **尚未取证**（推断为 zip 族），要做得先实测确定——若写成 `*/*`，会被塞进所有分享清单，代价很大。

### 6.2 接到意图之后做什么

- **路径 ②**：从意图的 `data` 取出网址 → 判断是不是目标站点（微信文章 `mp.weixin.qq.com`，以后可扩 B站等白名单）→ 是就调剪藏接口 → 存成剪藏记录 → 跳到记录页/显示进度条。
- **路径 ③**：从 `EXTRA_TEXT` 里**提取第一个网址** → 同上；提取不到网址（比如分享的是一段普通文字）→ 给个明确提示，不要静默失败。
- **共同点**：**抓取不在手机上做**。手机只负责「接住网址、转给服务器」，重活都在服务器（和现在一模一样）。

### 6.3 必须处理的边界（不做会很难看）

1. **兜底转发**：挂了「打开链接」的牌子后，用户点任何网页链接的「打开方式」里都会出现我们。**不是目标站点时必须把意图转交给系统浏览器**，否则用户会发现「点链接卡在一个不相干的 App 里」。
2. **捕获范围**：挂了「接收文本」牌子后，所有分享纯文本的场景都会出现我们。文本里没有网址时要能安静退出。
3. **用户可能设了默认浏览器**：那不影响微信自己画的面板（路径 ②），但会影响系统 chooser（路径 ③）。Android 13+ 的 chooser 还有「固定常用目标」的行为，我们可能不在首屏——需要引导文案。
4. **渠道归因**：同一个网址可能被三条路径重复送进来，沿用现有的「同一篇文章只存一条」去重（`clipLinkKey`）即可，不需要新机制。

### 6.4 ⚠️ 前置条件：手机必须能连上剪藏服务（**当前是拦路虎**）

现在剪藏服务**只绑宿主机的 `127.0.0.1:8787`**，电脑上是通过 SSH 隧道（本机 `8788` → VPS `8787`）访问的。**手机连不上这个隧道。**所以安卓入口做完之前，必须先让手机能访问到剪藏服务，二选一：

- **局域网方案**：手机和电脑在同一 Wi-Fi，服务绑到局域网 IP，手机填电脑的局域网地址（简单，但只在同一 Wi-Fi 下可用）；
- **上云方案**：服务在 VPS 上对外开（`CLIP_HOST=0.0.0.0`，容器已经在跑），手机通过**域名或公网 IP + 端口**访问（这正是 D9「剪藏服务对外开 + Bearer Token」的形态，需要用户提供域名或同意用 IP）。

> 这条要写进施工顺序：**「手机能访问剪藏服务」是安卓入口的硬前置**，不是做完再补的事。

## 8. 未知与风险（接手的 AI 请先看这里）

1. **路径 ① 的 zip 内部结构没看过**。不知道里面是 HTML 还是别的、图片怎么放、编码如何。**不允许在没实测前估工**。
2. **路径 ① 的 MIME 没取证**（日志缓冲已翻页）。要做得先把路径①重走一遍、在 chooser 里点个应用，抓那条 `wm_create_activity`。
3. **路径 ② 的面板规则是微信自家的**。今天的证据显示它是「纯能力匹配 + 两个自家推广位」，但微信随时可能加白名单/改筛选，**不能当作永远成立的地基**。
4. **没验证「我们的 App 装上去之后真的会出现在这三个列表里」**——今天只验证了「别的 App 为什么在里面」。真正的确认要等安卓壳做出来装上手机。
5. **手机端连接剪藏服务的问题尚未解决**（见 6.4），这是做安卓入口的先决条件。
