## 0 通用规则（每个任务都适用，务必先读）

### 0.1 上下文上限纪律（最重要）

1. **一个任务必须能在一轮对话内做完**。做不完就先交"最小可用版"并提交，把剩余部分作为**新任务追加到队列末尾**（编号顺延），不要硬撑。
2. **状态必须落文件**：每完成一个子步骤，更新该任务的「进度交接」栏与 `ops/运行状态.json`。**下一轮是全新会话，看不到你的上下文。**
3. **单轮不要同时改超过 5 个文件**；大文件分批改。
4. **上下文将满时**：把（已完成 / 改了哪些文件 / 下一步 / 未决问题）写进「进度交接」，提交，收尾。

### 0.2 提交规则

- 每个任务完成后 `git commit`（**不 push**）；中文提交信息**必须用 `git commit -F <文件>`**（cmd 下中文会乱码）。
- 提交前 `git status` 核对；不要提交 `node_modules/`、`server/data/`、`server/out/`、任何凭证。

### 0.3 硬约束

| 禁止 | 允许 |

### 0.4 技术栈（已定，照做）

- 服务端在 **`server/`**，**TypeScript + Node**；**不引入构建工具**（Node 24 原生直跑 `.ts`：`node src/cli.ts`）
- **依赖尽量为零**（本机 npm 不稳）：HTTP 用内置 `fetch`；SQLite 优先 `node:sqlite`，不可用则退化为 JSONL + 内存索引，**对外接口不变**
- 资源只存**编号** `assetId` + `provider`，**不存完整 URL**（G1）
- 消息获取以**轮询为主**（G2/G6）

### 0.5 通用验收

- 涉及代码：**必须实际跑起来**并贴出真实输出（不许"应该可以"）
- 抓取相关：以**图片成功/原文数**与**正文文字量**为客观指标
- 每个任务完成后更新本文件「状态 / 进度交接 / 失败记录」

### 0.6 超时接管（由探测会话执行）

- 每个任务都有「预估」分钟数；**超时线 = max(预估×2, 30) 分钟**
- 实际耗时超过超时线 → 探测会话把该任务状态改为 `超时·转末轮`、加入 `ops/运行状态.json` 的 `deferred`，然后**立即领下一个任务**
- 07:20 之后 `deferred` 里的任务各获得一次重试机会；07:50 后一律收工
